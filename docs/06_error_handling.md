# **검증과 오류 처리**

## **학습 목표**

- 오류를 입력, 자원, 데이터베이스, 서버 오류로 구분할 수 있다.
- FastAPI와 Pydantic의 요청 검증 흐름을 이해한다.
- `HTTPException`으로 404 응답을 만드는 방법을 설명할 수 있다.
- 오류 처리에서 계층별 책임을 구분할 수 있다.
- 테스트와 로그를 이용해 오류 원인을 확인할 수 있다.

## **1. 오류 처리의 목적**

오류 처리는 단순히 프로그램이 종료되지 않게 만드는 작업이 아니다. 요청을 더
처리할 수 없는 이유를 올바른 계층에서 판단하고, 클라이언트에는 적절한 HTTP
응답을 주며, 개발자가 원인을 추적할 정보는 보존해야 한다.

좋은 오류 처리는 다음 질문에 답한다.

- 잘못된 입력인가, 존재하지 않는 자원인가, 서버 내부 실패인가
- 클라이언트가 요청을 고쳐 다시 시도할 수 있는가
- 데이터베이스 변경이 일부만 남지는 않았는가
- 사용자에게 보여줄 정보와 로그에 남길 정보를 어떻게 구분할 것인가

## **2. 오류의 종류**

| 종류 | 예시 | 일반적인 응답 |
| --- | --- | --- |
| 입력 검증 오류 | 제목 누락, 잘못된 Path 타입 | 4xx |
| 자원 오류 | 존재하지 않는 To-do | `404 Not Found` |
| 충돌 또는 규칙 오류 | 허용되지 않는 상태 변경 | 4xx |
| 데이터베이스 오류 | 파일 접근 실패, commit 실패 | 5xx |
| 프로그래밍 오류 | 처리하지 않은 예외 | `500 Internal Server Error` |

오류를 모두 500으로 반환하면 사용자가 요청을 수정해야 하는 상황과 서버가
고장 난 상황을 구분할 수 없다.

## **3. Pydantic 입력 검증**

`TodoCreate`와 `TodoUpdate`는 Form 데이터가 가져야 할 형태를 정의한다.

```python
title: str = Field(min_length=1, max_length=100)
description: str | None = None
```

FastAPI는 Router 함수를 호출하기 전에 Form 값을 모델로 변환한다. 필수 값이
없거나 타입과 제약 조건이 맞지 않으면 함수 본문까지 들어가지 않고 검증 오류
응답을 만든다.

```text
HTTP 요청
  → Form 데이터 읽기
  → Pydantic 변환과 검증
  → 성공하면 Router 실행
  → 실패하면 오류 응답
```

HTML의 `required`와 `maxlength`도 사용자 입력을 돕지만 서버 검증은 반드시
유지해야 한다. HTTP 요청은 브라우저 밖에서도 보낼 수 있기 때문이다.

FastAPI의 기본 검증 오류는 보통 `422 Unprocessable Content`와 구조화된 오류
Body로 반환된다. SSR 서비스에서 검증 실패를 HTML Form에 다시 표시해야 한다면
별도의 예외 처리와 오류 Template 설계가 필요하다.

## **4. 존재하지 않는 자원 처리**

Repository의 `get_by_id`는 대상이 없을 때 `None`을 반환한다. Service도 이 의미를
유지하고 Router가 HTTP 상태 코드로 변환한다.

```python
todo = service.get_todo_by_id(todo_id)
if todo is None:
    raise HTTPException(
        status_code=status.HTTP_404_NOT_FOUND,
        detail="To-do를 찾을 수 없습니다.",
    )
```

각 계층의 표현은 다음과 같이 달라진다.

```text
Repository: 조회 결과가 없음
Service: TodoResponse | None
Router: HTTP 404 응답
```

Repository가 직접 `HTTPException`을 발생시키면 데이터 접근 계층이 FastAPI에
의존하게 된다. HTTP 의미는 Router에서 결정하는 편이 계층 책임에 맞다.

## **5. 변경 대상이 없는 경우**

수정, 완료, 삭제도 먼저 대상이 존재하는지 확인한다.

- 수정 결과가 `None`이면 404를 반환한다.
- 완료 결과가 `None`이면 404를 반환한다.
- 삭제 결과가 `False`이면 404를 반환한다.

존재하지 않는 id의 삭제 요청을 성공처럼 처리할 것인지 404로 처리할 것인지는
서비스 정책에 따라 달라질 수 있다. 현재 프로젝트는 사용자가 요청한 대상이
없다는 사실을 명확하게 알리기 위해 404를 선택했다.

## **6. 데이터베이스 오류와 트랜잭션**

`commit()` 중 오류가 발생하면 변경을 성공으로 응답해서는 안 된다. 같은
Session을 계속 사용할 경우 먼저 `rollback()`으로 실패한 트랜잭션 상태를
정리해야 한다.

```python
try:
    session.commit()
except Exception:
    session.rollback()
    raise
```

이 코드는 오류 처리 원리를 보여주는 예시이며 현재 Repository에 그대로 구현된
구조는 아니다. 요청 단위 Session이 종료되면 미확정 작업은 남지 않지만, 복잡한
트랜잭션이나 구체적인 오류 응답이 필요해지면 rollback 정책을 명시해야 한다.

데이터베이스 예외를 무조건 일반 메시지로 바꿔 버리면 원인과 traceback을 잃을 수
있다. 사용자 응답에는 내부 파일 경로나 SQL을 노출하지 않고, 개발 로그에는 원래
예외를 유지하는 방식이 필요하다.

## **7. 404와 500의 차이**

`404 Not Found`는 서버가 정상적으로 요청을 이해했지만 지정한 자원을 찾지 못한
상황이다. `500 Internal Server Error`는 서버 코드가 예상하지 못한 방식으로
실패한 상황이다.

```text
GET /todos/999
  → id 999가 없음
  → 예상한 분기
  → 404

GET /todos/1
  → Template 문법 오류
  → 예상하지 못한 서버 실패
  → 500
```

예상 가능한 자원 부재를 500으로 처리하면 서버 장애처럼 보이고, 실제 서버 오류를
404로 숨기면 문제를 찾기 어렵다.

## **8. 사용자 메시지와 개발자 정보**

오류 정보는 대상에 따라 구분한다.

### **8.1 사용자에게 필요한 정보**

- 요청을 완료하지 못했다는 사실
- 입력을 수정할 수 있는 구체적인 안내
- 다시 이동할 수 있는 화면이나 행동

### **8.2 개발자에게 필요한 정보**

- 예외 타입과 traceback
- 요청 Method와 Path
- 실패한 계층과 작업
- 재현에 필요한 입력 조건

데이터베이스 경로, 내부 코드, 전체 예외 문자열을 그대로 사용자에게 보여주면
불필요한 내부 정보가 노출될 수 있다. 반대로 로그 없이 사용자용 메시지만 남기면
원인 분석이 어려워진다.

## **9. SSR 오류 화면**

현재 404는 FastAPI의 기본 오류 응답으로 반환된다. 전체 서비스를 HTML 화면으로
통일하려면 404와 검증 오류를 렌더링하는 Template을 추가할 수 있다.

```text
오류 발생
  → 예외 핸들러
  → 오류 상태에 맞는 Template
  → 같은 상태 코드의 HTML 응답
```

오류 화면을 추가하더라도 상태 코드를 200으로 바꾸면 안 된다. 화면은 친절하게
보이더라도 HTTP 응답은 실제 결과를 정확하게 표현해야 한다.

## **10. 오류 처리 테스트**

오류 경로는 정상 경로와 별도로 검증한다.

```python
@pytest.mark.parametrize("path", ["/todos/999", "/todos/999/edit"])
def test_missing_todo_pages_return_not_found(client, path):
    response = client.get(path)
    assert response.status_code == 404
```

다음 조건도 필요에 따라 테스트할 수 있다.

- 제목이 없거나 100자를 초과한 Form 요청
- 정수가 아닌 `todo_id`
- 존재하지 않는 대상의 수정, 완료, 삭제
- 데이터베이스 commit 실패 시 부분 저장 여부
- 오류 화면의 상태 코드와 이동 링크

## **11. 오류를 진단하는 순서**

1. 실패한 요청의 Method와 URL을 확인한다.
2. 응답 상태 코드와 Body를 확인한다.
3. 서버 로그에서 최초 예외와 traceback을 찾는다.
4. Router 입력 검증, Service 분기, Repository 저장 순서로 범위를 좁힌다.
5. 같은 조건을 자동화된 테스트로 재현한다.
6. 수정 후 정상 경로와 오류 경로를 모두 다시 실행한다.

오류 메시지의 마지막 줄만 보고 원인을 단정하기보다 요청부터 저장까지 흐름을 따라
최초로 잘못된 상태가 만들어진 지점을 찾는 것이 중요하다.

## **프로젝트에서 확인하기**

- `app/schemas/todos.py`: 입력값 제약 조건
- `app/routers/todos.py`: HTTPException과 404 변환
- `app/services/todos.py`: 대상 없음과 업무 상태 처리
- `app/repositories/todos.py`: commit을 포함한 저장 처리
- `tests/test_todo_ui.py`: 404와 실제 요청 흐름 테스트

## **핵심 정리**

입력 검증 실패, 자원 부재, 데이터베이스 실패는 원인과 대응이 다르다. Pydantic은
Router 실행 전 요청 데이터를 검증하고, Router는 Service 결과를 적절한 HTTP
상태로 변환한다. 데이터베이스 변경은 트랜잭션 단위로 다뤄야 하며, 사용자에게
보여줄 안전한 메시지와 개발자가 진단할 원본 오류 정보를 구분해야 한다.
